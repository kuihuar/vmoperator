# 可观测性研发经验与排障（面试要点）

把 **Prometheus（指标）** 与 **Elasticsearch（日志）** 连成可落地的工程习惯，而不是孤立背概念。

## 1. 研发流程中的位置

- **设计阶段**：为关键用户路径定义 SLO（可用性、创建成功率、P95 延迟）；反推需要哪些指标与日志字段。
- **开发阶段**：指标命名与 label 规范评审；日志级别约定（Error 必含可操作信息）。
- **发布阶段**：仪表盘与告警随版本变更；灰度期间对比「错误率、队列深度、下游 API 429」。

## 2. 排障路径（可口述）

1. **告警/用户反馈** → 看对应 **SLO 面板**（是否全局还是单租户）。
2. **指标** 区分是「我们慢」还是「下游慢」（KubeVirt API、APIServer 429、存储挂载超时）。
3. **日志** 用 **trace/reconcile id** 拉一条时间线；必要时结合 **Kubernetes Events** 与 **Audit**。
4. **结论** 区分**代码缺陷、配置、容量、依赖升级**四类，避免只停在「重启就好」。

## 3. 常见坑（面试加分）

- **高基数 metrics** 导致 Prometheus 内存暴涨。
- **日志爆炸**：Debug 默认开启、或在循环内打印。
- **告警疲劳**：阈值过松或过紧；无 `for` 持续时间导致抖动。
- **缺少 exemplar / trace 关联**：仅有指标难以跳到具体请求（可提 OpenTelemetry 作为演进）。

## 4. 与 On-Call、文档

- **Runbook**：每条告警对应「确认步骤、缓解动作、升级路径」。
- **变更记录**：升级集群或 KubeVirt 时，记录前后核心指标对比截图或数据。

## 5. 一句话总结

可观测性的目标是 **缩短 MTTR**：用指标发现问题，用日志与事件缩小范围，用规范与 Runbook 把个人经验变成团队能力。
