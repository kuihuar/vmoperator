# K8s 资源创建流程（面试版）

本文将「一个资源从提交请求到最终可用」抽象为通用 K8s 流程，并结合当前项目 `Wukong -> VirtualMachine -> VirtualMachineInstance` 做映射，适合面试口述。

---

## 1. 一句话主线

**声明写入 API Server -> 控制器持续 Reconcile -> 依赖资源按顺序就绪 -> 下游控制器落地运行 -> 状态回写。**

---

## 2. 通用 8 步流程

1. **客户端提交期望状态**  
   `kubectl apply` 或业务 API 提交 YAML/JSON 到 Kubernetes API Server。

2. **API Server 准入与持久化**  
   经过认证、鉴权、准入校验（Schema / Admission）后，资源写入 etcd。

3. **控制器 Watch 到新增事件**  
   对应 Controller 收到 Add/Update 事件，进入 Reconcile 循环。

4. **初始化与防删保护**  
   控制器读取对象、做必要校验/默认化，并添加 Finalizer（保障删除前可清理子资源）。

5. **按依赖拓扑创建子资源**  
   先创建前置依赖，再创建主资源；未就绪则不进入下一步。

6. **检测就绪并重试（Requeue）**  
   若依赖尚未 Ready/Bound，Controller 返回 Requeue 或 RequeueAfter，等待下一轮协调。

7. **下游控制器真正执行落地**  
   主资源创建后，由其所属控制器完成调度、启动、挂载、网络接入等实际动作。

8. **状态回写与收敛**  
   Controller 将实际状态回写到 `status.phase` / `conditions`，直到达到 `Running/Ready` 或 `Error`。

---

## 3. 在本项目中的具体映射

### 3.1 资源关系

```text
Wukong (Owner)
├── NetworkAttachmentDefinition (Multus)
├── PersistentVolumeClaim / DataVolume (Storage)
└── VirtualMachine (KubeVirt)
    └── VirtualMachineInstance (Running VM)
```

### 3.2 创建顺序（面试高频）

1. 提交 `Wukong` CR；
2. `WukongReconciler` 触发 Reconcile；
3. 添加 Finalizer；
4. 处理网络：创建/复用 `NetworkAttachmentDefinition`；
5. 处理存储：按磁盘配置创建 `PVC` 或 `DataVolume`，等待 Bound；
6. 调用 `kubevirt.ReconcileVirtualMachine()` 创建/更新 `VirtualMachine`；
7. KubeVirt 创建 `VirtualMachineInstance` 并在节点拉起虚机；
8. Controller 同步 `Phase/Conditions`，从 `Pending/Creating` 逐步推进到 `Running`。

---

## 4. 关键状态与判断点

- **Phase**：`Pending -> Creating -> Running / Stopped / Error`
- **Conditions**：
  - `NetworksConfigured`
  - `VolumesBound`
  - `Ready`

面试可强调：**Condition 用于解释“卡在哪一步”**，Phase 用于表达整体生命周期。

---

## 5. 为什么要 Reconcile + Requeue

- Kubernetes 是最终一致性模型，依赖组件（存储、网络、调度）不是瞬时完成；
- Controller 通过幂等 Reconcile 持续“把现实拉向期望”；
- 临时失败（卷未绑定、调度未完成）并非错误终态，通常靠 Requeue 收敛。

---

## 6. 面试回答模板（30 秒）

「在 K8s 里资源创建是声明式的。请求先进入 API Server 并持久化，Controller watch 到后进入 Reconcile。它先做 Finalizer 和参数校验，再按依赖顺序创建子资源。我们项目是先网络 NAD、再存储 PVC/DataVolume，全部就绪后才创建 KubeVirt VM。随后由 KubeVirt 拉起 VMI 真正跑起来，最后把 Phase 和 Conditions 回写到 CR 状态。未就绪就 Requeue 重试，直到 Running 或 Error。」
